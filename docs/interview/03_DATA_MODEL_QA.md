# 3. 데이터 모델 예상 질문과 답변

[목차](README.md) · [원본 ERD](../01_ERD.md)

답변은 현재 구현을 설명하는 초안입니다. 대안의 장점도 인정하고, 현재 선택이 모든 금융 시스템에 보편적인 정답이라고 주장하지 않습니다.

## 3.1 D01. 왜 저금통을 별도 계좌로 만들었습니까?

저금통도 독립적인 잔액·상태·계좌번호·입출금 기록을 가지기 때문입니다. ACCOUNT에 공통 금융 속성을 두고 parent_account_id로 근거 입출금계좌와 연결했습니다. COINBOX에는 동전모으기 활성 여부처럼 저금통에만 필요한 고객별 설정을 두었습니다.

**꼬리질문:** 단순히 입출금계좌의 잔액 일부를 표시하는 기능이라면 별도 계좌가 필요합니까?

그런 요구라면 논리적인 자금 구분 모델도 가능합니다. 이 과제에서는 가입·해지와 독립적인 거래 기록을 다루므로 별도 계좌 모델을 선택했습니다.

## 3.2 D02. ACCOUNT와 ACCOUNT_CONTRACT를 왜 분리했습니까?

ACCOUNT는 현재 운영 상태와 잔액, ACCOUNT_CONTRACT는 상품 가입 관계와 가입 당시 상품 버전을 관리합니다. 계좌의 거래 가능 여부와 계약 조건은 변경 이유가 다르므로 분리했습니다. 그 대신 두 데이터가 모순되지 않도록 상태 전환을 같은 업무 트랜잭션으로 관리해야 합니다.

계약 테이블이 존재한다고 상품 전환·계약 이력 관리용 API까지 구현된 것은 아닙니다. 현재 주요 쓰기 경로는 가입과 해지입니다.

## 3.3 D03. PRODUCT·PRODUCT_VERSION·COINBOX_POLICY가 모두 필요합니까?

PRODUCT는 상품군과 이름, PRODUCT_VERSION은 적용 기간과 버전, COINBOX_POLICY는 버전별 저금통 한도를 관리합니다. 계약이 어느 정책에 가입했는지 유지하려고 구분했습니다.

다만 정책이 단일 고정 값이고 변경 가능성을 전혀 다루지 않는 과제라면 더 단순한 모델도 가능합니다. 현재 선택은 정책 추적을 얻는 대신 테이블·조인·관리 규칙이 늘어나는 비용을 감수한 설계입니다.

현재 ProductType은 DEMAND_DEPOSIT(입출금통장), BUSINESS_DEMAND_DEPOSIT(개인사업자통장), COINBOX(저금통), MEETING_ACCOUNT(모임통장), INSTALLMENT_SAVING(적금), FIXED_DEPOSIT(정기예금)입니다. Enum에 존재하는 모든 상품의 업무를 구현한 것은 아닙니다.

## 3.4 D04. ACCOUNT.product_type은 왜 중복 저장했습니까?

계좌의 현재 상품 유형을 판단할 때 계약과 상품 버전을 매번 조인하지 않기 위한 의도적인 비정규화입니다. 현재 유형 조회가 단순해지는 대신 계약이 가리키는 상품과 불일치할 위험이 생깁니다.

향후 상품 전환을 구현한다면 계약 변경과 ACCOUNT.product_type 갱신을 같은 트랜잭션에 묶고 정합성 테스트를 추가해야 합니다. 측정한 자료가 없으므로 조인을 줄여 몇 퍼센트 빨라졌다고 말하지 않습니다.

## 3.5 D05. 계약의 상품 유형은 어떻게 결정됩니까?

ACCOUNT_CONTRACT는 product_version_id로 PRODUCT_VERSION을 참조하고, 해당 버전의 PRODUCT에서 상품 유형을 확인합니다. ACCOUNT.product_type은 현재 계좌 운영을 위한 조회 값이며, 계약은 가입한 상품 버전을 기준으로 해석합니다. 두 경로가 같은 상품을 가리키도록 가입과 상태 전환의 정합성을 관리해야 합니다.

## 3.6 D06. COINBOX.account_id는 어떤 관계를 나타냅니까?

동전모으기 설정은 고객이 사용하는 저금통 계좌에 종속되기 때문입니다. account_id에 UK를 두어 계좌 하나에 저금통 설정이 하나만 연결되도록 했습니다. 정책을 판단할 때는 해당 계좌의 계약을 통해 상품 버전을 찾습니다.

이 구조도 향후 한 계좌에 복수의 동시 유효 계약을 허용하면 계약 선택 규칙이 필요합니다. 현재 '최신 계약 조회'가 모든 복잡한 계약 모델의 해답은 아닙니다.

## 3.7 D07. COINBOX_POLICY에서 max_amount를 관리하는 이유는 무엇입니까?

한도는 기본적으로 가입자 개인 설정이 아니라 상품 버전의 정책이기 때문입니다. COINBOX_POLICY에 버전별 한도를 저장하고 동일 버전의 가입자가 같은 기준을 참조합니다. 고객별 특별 한도가 요구된다면 별도 예외 정책의 우선순위를 설계해야 합니다.

## 3.8 D08. 정책을 변경하면 기존 가입자에게도 바로 적용됩니까?

현재 계약은 product_version_id를 보관하고 배치도 그 버전의 정책을 조회합니다. 따라서 새로운 버전 생성만으로 기존 계약이 새 정책을 사용하는 것은 아닙니다. 신규 가입은 개설일에 유효한 버전을 선택합니다.

기존 버전의 정책 행을 직접 수정하면 캐시가 새로 생성되는 이후 실행에서 기존 가입자에게도 바뀐 값이 읽힐 수 있습니다. 따라서 '버전별 정책은 불변으로 운영한다'는 원칙과 DB 행을 아무나 수정할 수 없게 하는 운영 통제를 구분해야 합니다.

## 3.9 D09. FINANCIAL_TRANSACTION과 ACCOUNT_ENTRY의 차이는 무엇입니까?

FINANCIAL_TRANSACTION은 자금 이동 사건 한 건을 나타내며, ACCOUNT_ENTRY는 그 사건이 각 계좌에 반영된 방향과 잔액 변화를 나타냅니다. 예를 들어 850원 이체는 거래 한 건과 출금·입금 원장 각각 한 건으로 기록합니다.

거래 유형은 TRANSFER만 사용합니다. 비우기·동전모으기·해지는 EntryCode와 적요로 업무 의미를 구분합니다. 고객 계좌별 원장 모델이며 총계정원장과 완전한 회계 복식부기까지 구현한 것은 아닙니다.

## 3.10 D10. 원장이 있는데 ACCOUNT.balance도 저장해야 합니까?

매 요청마다 전체 원장을 합산하지 않고 현재 잔액과 출금 가능 여부를 빠르게 판단하기 위해 저장했습니다. 계좌 잔액과 거래 기록을 같은 트랜잭션으로 반영하는 것이 중요합니다.

운영에서는 별도의 대사로 일치 여부를 확인할 수 있습니다. 다만 이 프로젝트의 초기 잔액과 테스트용 직접 증감은 원장을 생성하지 않으므로, 현재 DB에서 원장 합계만 계산하면 모든 계좌 잔액이 일치한다고 말할 수는 없습니다.

## 3.11 D11. 원장의 before·after와 적요를 왜 저장합니까?

거래 시점에 사용한 잔액 변화와 고객 통장에 표시한 문구를 추적하기 위해 저장합니다. 적요는 저장 시점의 설명을 보존하므로 Enum의 현재 description이 나중에 바뀌어도 과거 표시를 재구성할 수 있습니다.

새 원장을 생성할 때 기본 문구는 enum.getDescription()을 사용합니다. 원장을 나중에 다시 조회할 때 현재 Enum 설명으로 무조건 덮어써야 한다는 뜻은 아닙니다. 수정·삭제 업무는 제공하지 않지만 DB 차원에서 불변 원장을 강제한 것은 아닙니다.

## 3.12 D12. 어떤 유일 제약이 중요합니까?

| 제약 | 역할 |
|---|---|
| ACCOUNT.account_number | 같은 계좌번호의 저장을 방지합니다. |
| PRODUCT.product_type | 상품군 업무 유형의 중복을 방지합니다. |
| PRODUCT_VERSION(product_id, version_number) | 상품 내 버전 번호 중복을 방지합니다. |
| COINBOX.account_id | 계좌별 저금통 설정 한 개를 보장합니다. |
| COINBOX_POLICY.product_version_id | 상품 버전별 저금통 정책 한 개를 보장합니다. |
| ACCOUNT_DAILY_BALANCE(account_id, balance_date) | 계좌·기준일별 잔액 행 중복을 방지합니다. |
| COIN_SAVING_EXECUTION(coinbox_id, execution_date) | 저금통·실행일별 처리 행 중복을 방지합니다. |
| COIN_SAVING_EXECUTION.transaction_id | 연결된 금융거래의 중복 연결을 방지합니다. 건너뜀은 null입니다. |

고객당 이용 중인 저금통 한 개, 계좌당 ACTIVE 계약 한 개, 버전 적용 기간의 비중첩을 직접 강제하는 DB 유일 제약은 현재 없습니다. PK·UK가 참조 무결성이나 모든 업무 규칙까지 대신하지 않습니다.

## 3.13 D13. 실행 이력의 거래 ID는 왜 nullable입니까?

업무상 SKIPPED는 처리 결과가 있지만 자금 이동은 없으므로 연결할 금융거래가 없습니다. SUCCESS에는 거래 ID를 연결합니다. 따라서 거래와 실행 이력 사이에는 양쪽 모두 선택적인 일대일 관계가 가능합니다. 모든 이체가 동전모으기인 것도 아니고, 모든 실행 결과가 이체를 만드는 것도 아닙니다.

## 3.14 D14. JPA 연관관계를 사용하지 않으면 FK도 없어야 합니까?

아닙니다. Java 객체 연관관계와 DB 물리 외래 키는 별개의 선택입니다. 현재 엔티티는 Long 또는 Enum으로 참조 값을 보관해 조회·잠금을 명시적으로 제어하며, 이러한 매핑만으로는 Hibernate가 물리 FK를 자동 생성하지 않습니다.

ERD의 FK는 논리 참조입니다. SQL 마이그레이션으로 물리 FK를 추가하면서도 Java에서는 Long 참조를 유지할 수 있습니다. 현재는 서비스 검증에 의존하므로 직접 SQL이나 다른 쓰기 경로에는 취약할 수 있습니다.

**꼬리질문: 그렇다면 이 과제에서 물리 외래 키를 설정하지 않은 이유는 무엇입니까?**

> 엔티티 간 관계는 ID로 참조하고 Hibernate의 자동 DDL을 사용했기 때문에, 현재 물리 외래 키는 생성되지 않습니다. 별도의 DDL로 외래 키를 추가하는 부분까지는 구현하지 않았습니다.
>
> 서비스에서 참조 대상의 존재와 관계를 검증하고 있지만, 직접 SQL이나 다른 쓰기 경로까지 참조 무결성을 보장하지는 못한다는 한계가 있습니다.
>
> JPA 연관관계와 물리 외래 키는 별개의 선택이므로, 운영 수준으로 보완한다면 현재의 ID 참조 방식은 유지하면서 마이그레이션으로 외래 키를 추가하겠습니다.

핵심은 외래 키가 불필요해서 제외했다는 주장이 아니라, 현재 구현의 보장 범위와 DB 차원의 보완 필요성을 설명하는 것입니다. 측정하지 않은 성능 저하나 금융권 관행을 미사용 이유로 들지 않습니다. 서비스의 업무 검증과 DB의 참조 무결성 제약은 서로 보완하는 수단입니다.

## 3.15 D15. 금액은 왜 Long이고 계좌번호는 왜 String입니까?

금액은 단일 원화의 정수 원 단위만 다루므로 Long으로 표현했습니다. 소수 단위·환율·이자를 계산한다면 BigDecimal과 명시적인 반올림 규칙을 검토해야 합니다. long도 범위가 유한하므로 현재 일반 계좌 입금에서는 Math.addExact로 오버플로를 검사합니다.

계좌번호는 계산 대상이 아닌 식별 문자열입니다. 하이픈 없는 13자리로 저장하고 앞 4자리는 일반·개인사업자 입출금 3333, 저금통 3310, 모임통장 7979를 사용합니다. 중앙 채번·체크 디지트는 구현하지 않았습니다.

## 3.16 D16. Snowflake의 장단점과 JSON 문자열 반환 이유는 무엇입니까?

DB INSERT 전에 식별자를 만들 수 있고 시간·노드·순번을 조합한 Long 키를 사용합니다. 현재 코드는 시간 41비트, 노드 10비트, 순번 12비트를 사용하며 한 인스턴스의 생성 메서드를 synchronized로 보호합니다.

**왜 AUTO_INCREMENT나 UUID 대신 선택했습니까?**

> 계좌·계약·원장처럼 서로 참조하는 데이터를 만들 때 저장 전에 식별자를 확보하고, DB 채번에 의존하지 않는 Long 대리 키를 공통으로 사용하려고 선택했습니다. 다만 현재 단일 DB 과제에서 Snowflake가 필수는 아니며, 생성기 운영 부담이 작은 AUTO_INCREMENT도 충분히 합리적인 대안입니다.

| 대안 | 비교 기준 |
|---|---|
| AUTO_INCREMENT | DB가 채번을 담당하므로 애플리케이션의 노드·시계 관리가 단순합니다. 참조할 ID를 확보하는 시점은 DB INSERT와 연결됩니다. |
| UUID | 애플리케이션에서 선발급할 수 있는 대안입니다. 128비트 값을 어떤 DB 타입에 저장할지, 시간순 정렬이 필요한지와 사용할 UUID 버전을 함께 결정해야 합니다. UUID가 모두 무작위 정렬인 것은 아닙니다. |
| 현재 Snowflake | 저장 전 Long ID를 확보하고 시간 정보를 포함합니다. 대신 노드 할당·시계·생성기 상태를 관리해야 하며, ID 순서를 전역 커밋 순서로 해석할 수는 없습니다. |

대신 노드 ID 중복과 시계 역행을 관리해야 합니다. 현재 노드 ID는 0으로 고정되어 있으므로 설정 그대로 다중 인스턴스를 운영하면 안 됩니다. 시간 역행은 예외로 중단하며 자동 복구 체계까지 구현한 것은 아닙니다.

큰 정수를 JavaScript Number로 다룰 때 생기는 정밀도 손실을 피하려고 외부 JSON ID는 문자열로 반환합니다. Java Long과 DB BIGINT의 정확성이 브라우저의 숫자 표현까지 보장하지는 않습니다.

선발급 ID가 JPA INSERT 최적화까지 보장하지는 않습니다. 실제 save 경로는 [J09](06_TECH_TEST_OPERATIONS_QA.md), 생성기 동시성은 같은 문서의 J15에서 다룹니다. 처리량이나 인덱스 성능을 비교 측정해 선택했다고 설명하지 않습니다.

## 3.17 D17. Enum 문자열과 9999-12-31의 트레이드오프는 무엇입니까?

EnumType.STRING은 저장 값을 읽기 쉽고 Enum 선언 순서 변경에 영향을 받지 않는 장점이 있습니다. 다만 Enum 이름을 바꾸면 데이터·API 호환성을 검토해야 하며 문자열 저장 공간도 필요합니다.

종료일의 9999-12-31은 무기한을 나타내는 규약으로, null 분기 없이 기간 조건을 작성할 수 있습니다. 실제 종료 때는 종료일을 기록하고, 유효성은 시작일 포함·종료일 제외 조건으로 판단합니다. 다른 시스템과 연동할 때 sentinel의 의미와 날짜 범위를 합의해야 합니다. 모든 날짜 컬럼이 null 불가라는 뜻은 아닙니다.

## 3.18 D18. 자연 키와 대리 키의 차이는 무엇이며, 이 과제에서는 왜 대리 키를 선택했습니까?

**자연 키**는 계좌번호처럼 업무적으로 의미 있는 값으로 구성된 키입니다. 이를 PK로 선택하면 별도 식별자를 만들지 않아도 되며, 해당 업무 값의 유일성을 PK로 보장할 수 있습니다. 다만 업무 정책에 따라 키 값이 달라지면 참조하는 FK에도 영향이 생기고, 복합키라면 다른 테이블의 참조 구조가 복잡해질 수 있습니다.

**대리 키**는 업무 값과 별도로 생성한 식별자입니다. 이 과제의 Snowflake ID가 해당합니다. 업무 정책과 데이터 식별자를 분리하고 단일 ID로 참조할 수 있는 장점이 있습니다. 대신 서로 다른 ID를 가진 행에 같은 업무 값이 들어갈 수 있으므로, DB에서 보장할 업무 유일성에는 별도의 Unique Constraint가 필요합니다.

**면접 답변**

> 업무 정책과 데이터 식별자를 분리하고, 다른 테이블에서 참조할 때 구조를 단순하게 만들기 위해 Snowflake 기반 대리 키를 사용했습니다. 계좌번호나 저금통별 실행일처럼 유일해야 하는 업무 값에는 별도의 Unique Constraint를 적용했습니다.

| 대상 | 대리 키 PK: 행 식별 | 별도 UK: 업무 유일성 |
|---|---|---|
| ACCOUNT | account_id | account_number |
| ACCOUNT_DAILY_BALANCE | account_daily_balance_id | (account_id, balance_date) |
| COIN_SAVING_EXECUTION | execution_id | (coinbox_id, execution_date) |

핵심은 **이 과제에서 PK는 행 식별, 별도 UK는 업무 유일성 보장으로 역할을 나누었다**는 점입니다. PK 자체도 유일성을 보장하며, 자연 키를 PK로 사용하면 두 역할을 함께 수행할 수 있습니다.

자연 키가 무조건 나쁜 선택은 아닙니다. 업무상 유일하고 null이 없으며, 변경 가능성이 거의 없는 단순한 값이라면 자연 키도 충분히 선택할 수 있습니다. BIGINT 같은 자료형 자체가 자연 키와 대리 키를 구분하는 기준은 아닙니다.

모든 업무 규칙을 UK로 보장했다고 설명하지는 않습니다. 예를 들어 고객당 이용 중인 저금통 한 개는 현재 별도의 UK 없이 고객 행 잠금 규약으로 관리합니다.
