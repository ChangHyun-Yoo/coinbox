# 4. 트랜잭션·동시성 예상 질문과 답변

[목차](README.md) · [추가 검증과 한계](07_DESIGN_REVIEW_AND_MOCK_INTERVIEW.md)

## 4.1 T01. @Transactional만 있으면 동시성 문제가 해결됩니까?

아닙니다. 트랜잭션으로 여러 변경을 함께 확정하는 것과, 동시에 읽은 값을 이용한 경쟁을 제어하는 것은 구분해야 합니다. 두 요청이 잔액 100원을 읽고 각각 70원 출금을 판단하면 격리 수준과 쓰기 방식에 따라 문제가 생길 수 있습니다. 이 과제는 변경 대상 계좌를 비관적으로 잠그고 출금 조건을 확인하도록 구성했습니다.

## 4.2 T02. 이 과제에서 ACID를 설명해 보십시오.

- 원자성: 이체의 두 잔액과 거래·원장이 함께 성공하거나 롤백됩니다.
- 일관성: 잔액 부족 방지, 거래와 계좌 원장 연결 등 업무 규칙과 DB 제약을 함께 적용합니다. DB가 업무 규칙을 자동으로 알아주는 것은 아닙니다.
- 격리성: 경쟁하는 금융 변경을 계좌 잠금으로 조정합니다.
- 지속성: 커밋된 결과의 보존은 DB·스토리지의 내구성 설정에 의존합니다. 복제·백업까지 과제에서 구현한 것은 아닙니다.

## 4.3 T03. 신규 가입 때 고객을 잠그는 이유는 무엇입니까?

고객이 서로 다른 근거계좌로 동시에 저금통을 개설할 수 있기 때문입니다. 근거계좌만 잠그면 요청들이 서로 다른 행을 잠가 모두 '저금통 없음'을 판단할 수 있습니다. 항상 존재하는 고객 행을 공통 잠금 대상으로 사용해 고객 단위 가입을 직렬화했습니다.

고객 잠금 이후 저금통 존재 여부를 확인해야 합니다. 존재하지 않는 저금통 행을 잠그면 된다는 설명은 피합니다.

## 4.4 T04. 애플리케이션 서버가 두 대여도 고객 잠금이 유효합니까?

같은 DB를 사용하고 모든 경쟁 요청이 동일한 고객 행의 DB 잠금을 획득하면 서버 인스턴스가 달라도 조정됩니다. Java synchronized와 달리 한 JVM 안에서만 동작하는 잠금이 아닙니다. 단, 다른 서비스나 직접 SQL이 잠금 규약을 지키지 않으면 고객당 한 개라는 규칙을 우회할 수 있습니다.

## 4.5 T05. 근거계좌도 잠그는 이유는 무엇입니까?

고객 단위 잠금은 중복 가입을 조정하고, 계좌 잠금은 선택 계좌의 상태나 다른 계좌 변경과의 경쟁을 조정합니다. 보호하는 업무 조건이 다릅니다. 계좌 상태를 바꾸는 다른 경로도 일관된 잠금·변경 규칙을 따라야 합니다.

## 4.6 T06. 비관적 잠금 대신 낙관적 잠금은 어떻습니까?

충돌이 드물고 재시도 비용이 작다면 version 기반 낙관적 잠금도 대안입니다. 이 과제는 잔액 확인과 두 계좌·거래·원장을 묶는 변경을 명시적으로 직렬화하려고 비관적 잠금을 선택했습니다.

비관적 잠금은 대기가 생기고 낙관적 잠금은 충돌 시 재시도가 필요합니다. 실제 충돌률·응답 시간·재시도 비용을 측정하지 않았으므로 금융 시스템은 항상 비관적 잠금이어야 한다고 말하지 않습니다.

## 4.7 T07. 조건부 UPDATE로 출금하면 잠금 조회가 불필요하지 않습니까?

`UPDATE ... SET balance = balance - :amount WHERE balance >= :amount`와 영향 행 수 확인으로 한 계좌의 초과 출금을 방어할 수 있습니다. 다만 두 계좌의 상태·관계 검증, 입금, 원장 before/after, 전체 롤백을 함께 설계해야 합니다.

현재 일반 이체는 잠금 조회 후 엔티티 변경 방식입니다. 테스트용 출금 API의 조건부 UPDATE는 원장 없는 보조 기능이므로 그대로 금융 이체 설계의 대체물이라고 볼 수 없습니다.

## 4.8 T08. 두 계좌를 오름차순으로 잠그는 이유는 무엇입니까?

A→B와 B→A 요청이 각자 출금계좌부터 잠그면 서로 상대 계좌를 기다리는 순환 대기가 생길 수 있습니다. 요청 방향과 무관한 계좌 ID 순서로 잠금 조회를 통일해 교착 가능성을 줄였습니다.

SQL의 ORDER BY만으로 모든 실행 계획과 모든 테이블에 대한 교착이 없어지는 것은 아닙니다. 짧은 트랜잭션, 적절한 인덱스, 교착 로그 분석과 재시도 정책도 필요합니다. [MySQL 공식 문서](https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlocks-handling.html)

## 4.9 T09. 실제 잠금 순서를 설명해 보십시오.

| 업무 | 현재 코드의 잠금 조회 순서 |
|---|---|
| 개설 | CUSTOMER → 선택 ACCOUNT |
| 비우기 | 두 ACCOUNT의 ID 오름차순 조회 |
| 동전모으기 | 두 ACCOUNT의 ID 오름차순 조회 → COINBOX → 최신 ACCOUNT_CONTRACT |
| 해지 | CUSTOMER → 두 ACCOUNT의 ID 오름차순 조회 → COINBOX → 최신 ACCOUNT_CONTRACT |

개설 전 조회나 후보 조회에는 비관적 잠금을 걸지 않습니다. 표는 애플리케이션이 요청하는 쿼리 순서이며 DB 내부의 모든 인덱스 잠금 순서를 증명한 것은 아닙니다.

## 4.10 T10. 조인 쿼리에 FOR UPDATE를 붙이면 여러 행이 잠깁니까?

가능합니다. 잠금 범위는 반환 행 개수만이 아니라 DBMS, 인덱스, 실행 계획, 조회 조건과 격리 수준의 영향을 받습니다. 여러 테이블을 조인했다고 무조건 모든 테이블 전체가 잠기는 것도 아니며, 결과 한 행이라고 항상 잠금 하나만 생기는 것도 아닙니다.

현재 핵심 쓰기 경로는 계좌·저금통·계약을 별도 잠금 쿼리로 조회해 대상과 업무 순서를 드러냈습니다. 실제 잠금 범위는 실행 계획과 DB 잠금 정보로 확인해야 합니다. [MySQL 잠금 설명](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

## 4.11 T11. 공통 이체에서 상품과 양쪽 계약까지 확인합니까?

아닙니다. 공통 서비스는 계좌 존재·서로 다른 계좌·양쪽 ACTIVE·양수 금액·잔액 충분 여부와 거래·원장 생성을 담당합니다. 상품별 계약 규칙은 상위 업무 서비스의 책임으로 분리했습니다.

정확히는 비우기는 저금통 유형 등을 확인하되 계약 조회는 하지 않습니다. 동전모으기와 해지는 저금통 계약을 확인합니다. 양쪽 계약을 모든 이체에서 검사한다고 설명하면 실제 구현과 다릅니다.

## 4.12 T12. 계약이 해지됐는데 계좌가 ACTIVE이면 어떻게 됩니까?

현재 공통 이체의 판단만으로는 그 모순을 발견하지 못합니다. 계좌의 거래 가능 상태를 운영 판단 기준으로 사용하려면 계약 종료와 계좌 종료를 같은 트랜잭션으로 관리하고 우회 쓰기를 막아야 합니다.

현재 해지는 두 상태를 함께 변경하지만 모든 미래 경로를 자동으로 보장하지는 않습니다. 모순이 가능한 업무가 추가되면 계약 검증 강화나 거래 가능 상태를 계산하는 공통 정책을 검토해야 합니다.

## 4.13 T13. MANDATORY가 잠금을 보장합니까?

아닙니다. MANDATORY는 기존 트랜잭션에 참여하고, 트랜잭션이 없으면 예외를 발생시킵니다. 이미 필요한 잠금을 획득했는지나 전달 객체가 현재 영속성 컨텍스트의 관리 상태인지는 검증하지 않습니다.

transferLocked와 transferAllLocked는 호출자가 같은 트랜잭션에서 두 계좌를 잠갔다는 사용 규약을 전제로, 전달받은 계좌를 재조회하지 않고 사용하는 메서드입니다. 이름·접근 범위·호출 경로·테스트로 오용을 줄여야 합니다. [Spring Propagation](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/transaction/annotation/Propagation.html)

## 4.14 T14. REQUIRED와 REQUIRES_NEW를 여기서 어떻게 구분합니까?

일반 @Transactional 메서드는 기본 REQUIRED로 상위 트랜잭션이 있으면 참여합니다. 따라서 동전모으기의 이체와 실행 이력은 청크 트랜잭션에서 함께 확정됩니다.

이체만 REQUIRES_NEW로 분리하면 외부 실행 이력 저장이 실패해도 자금 이동이 먼저 커밋될 수 있으므로 현재 업무의 원자성을 깨뜨릴 수 있습니다. 실패 로그를 독립 저장하는 복구 설계는 별도 검토 대상이며 현재 구현되어 있지 않습니다. [Spring 전파 옵션](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/transaction/annotation/Propagation.html)

## 4.15 T15. 예외가 발생하면 항상 롤백됩니까?

기본 Spring 선언적 트랜잭션은 RuntimeException과 Error를 롤백 대상으로 처리하며 checked exception은 별도 설정을 확인해야 합니다. 현재 업무 예외는 RuntimeException 계열이며 예상하지 못한 저장 실패도 밖으로 전파됩니다.

예외를 잡고 정상 반환하거나 이미 rollback-only인 트랜잭션에서 계속 진행하는 경우도 구분해야 합니다. 또한 같은 객체 내부 호출은 프록시를 통과하지 않아 메서드의 별도 트랜잭션 설정이 적용되지 않을 수 있습니다. [Spring @Transactional](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)

## 4.16 T16. FOR UPDATE로 재조회하면 Java 객체도 최신입니까?

DB의 잠금 읽기와 JPA 영속성 컨텍스트의 객체 상태는 구분해야 합니다. 같은 엔티티가 이미 관리되고 있다면 조회 SQL을 다시 실행했다는 이유만으로 필드가 반드시 새 DB 값으로 덮어써졌다고 가정하면 안 됩니다. 필요한 경우 조회 순서를 바꾸거나 refresh 등 명시적인 갱신 전략을 검토합니다.

현재 비우기·해지는 잠금 전에 저금통 Account를 조회하는 경로가 있으므로 경쟁 중 객체 최신성은 추가 통합 테스트 대상입니다. 여기서는 실제 오류를 재현하거나 수정하지 않았으며, '모든 경쟁 상황에서 최신 잔액을 검증했다'고 단정하지 않습니다. [Jakarta Persistence EntityManager·refresh](https://jakarta.ee/specifications/persistence/3.2/apidocs/jakarta.persistence/jakarta/persistence/entitymanager)

## 4.17 T17. REPEATABLE READ와 잠금 읽기의 차이는 무엇입니까?

InnoDB의 일반 일관 읽기는 스냅샷을 사용하고, 잠금 읽기는 행 잠금을 동반하는 현재 데이터 읽기로 다뤄야 합니다. 격리 수준에 따라 일반 SELECT가 같은 트랜잭션에서 어떤 버전을 보는지도 달라집니다.

특히 고객 잠금 전에 다른 일반 조회로 스냅샷을 만들거나 조회 경로를 변경하면 중복 존재 확인에 미치는 영향을 다시 검증해야 합니다. 프로젝트 코드에서 격리 수준을 명시적으로 바꾸지는 않으므로 실제 DB 세션 설정 확인 없이 단정하지 않습니다. [InnoDB 일관 읽기](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)

## 4.18 T18. 온라인 요청도 멱등성을 보장합니까?

배치의 일별 업무 키와 달리 온라인 비우기에는 요청 ID를 저장하고 성공 응답을 재생하는 기능이 없습니다. 잔액이 비어 있으면 반복 요청을 거부하지만 그 사이 새로운 돈이 들어오면 같은 요청 재전송이 새 잔액을 다시 비울 수 있습니다.

따라서 상태 기반 방어와 요청 단위 멱등성을 구분해야 합니다. 운영에서는 고객·요청 키·요청 내용·처리 상태·응답을 함께 관리하고, 같은 키의 다른 요청 본문을 거부하는 정책이 필요합니다. 해지의 반복 예외 응답도 최초 응답 재생과는 다릅니다.

## 4.19 T19. UK 충돌을 잡고 같은 트랜잭션에서 계속하면 됩니까?

일괄적으로 그렇게 처리하면 안 됩니다. 제약 위반 이후 트랜잭션 상태와 예외가 발생한 시점은 JPA·DB 동작에 영향을 받습니다. 금융 변경과 이력을 함께 롤백한 뒤 중복 업무인지 분류하고 새로운 트랜잭션에서 확인하는 설계 등을 검토해야 합니다.

현재 사전 중복 확인과 잠금으로 정상 경로의 중복을 걸러내며 UK는 최종 방어입니다. 모든 UK 충돌을 정상 DUPLICATE 응답으로 변환하는 범용 복구 로직까지 구현한 것은 아닙니다.

## 4.20 T20. 동전모으기와 해지가 동시에 실행되면 어떻게 설명합니까?

두 업무가 같은 계좌·저금통·계약을 잠그므로 해당 구간의 변경은 순차적으로 진행하도록 설계했습니다. 먼저 동전모으기가 완료되면 해지는 그 결과를 포함해 잔액을 회수해야 하고, 해지가 먼저 완료되면 배치는 종료된 상태나 꺼진 설정을 보고 자금 이동을 하지 않아야 합니다.

이는 의도한 정합성 결과입니다. 잠금 순서뿐 아니라 영속성 컨텍스트 최신성과 실제 경쟁 테스트까지 확인해야 보장을 주장할 수 있습니다. 현재 동일 후보 중복 실행 테스트와 이체 경쟁 테스트가 있다고 모든 교차 업무 조합이 검증된 것은 아닙니다.
