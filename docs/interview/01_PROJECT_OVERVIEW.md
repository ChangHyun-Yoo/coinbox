# 1. 과제 전체 요약

[면접 준비 목차](README.md) · [업무 E2E](02_BUSINESS_FLOWS.md)

## 1.1 한 문장으로 설명하기

고객의 입출금계좌에 연결된 저금통의 가입·비우기·동전모으기·해지를 구현하고, 자금 이동의 원자성과 거래 추적, 동시성 제어와 일별 중복 저축 방지를 중점적으로 설계한 백엔드 과제입니다.

## 1.2 1분 소개 답변

> 저금통의 신규 가입, 비우기, 자동저축인 동전모으기와 해지를 구현했습니다. 저금통을 별도 계좌로 모델링하고 근거 입출금계좌와 연결했습니다. 가입 시에는 고객과 근거계좌를 잠가 중복 개설과 상태 변경 경쟁을 제어했습니다. 자금 이동은 공통 당행 이체 서비스로 모아 잔액 변경, 금융거래 한 건과 계좌 원장 두 건을 같은 트랜잭션으로 처리했습니다. 동전모으기는 Spring Batch로 후보를 페이징 조회하고 저금통별로 검증·이체·실행 이력을 처리했습니다. 같은 저금통과 실행일의 중복 처리는 복합 유일 키로 방어했습니다. 설계 문서뿐 아니라 MySQL Testcontainers 기반 테스트와 실행 환경도 함께 구성했습니다.

실제로 설명할 때는 문장을 모두 외우기보다 `업무 네 가지 → 데이터 모델 → 금융 정합성 → 배치 → 검증` 순서를 기억합니다.

## 1.3 3분 소개의 구성

1. **문제와 범위**: 고객이 사용하는 네 업무를 구현했습니다. 이자·수수료·취소·정정·공식 금융 마감은 제외했습니다.
2. **모델**: 계좌는 현재 잔액과 상태, 계약은 가입한 상품 버전, 정책은 버전별 한도, 저금통 설정은 고객별 동전모으기 활성 여부를 관리합니다.
3. **온라인 처리**: 가입은 고객 단위로 직렬화합니다. 비우기와 해지는 연결된 두 계좌 사이의 자금 이동을 공통화합니다.
4. **배치 처리**: 잔액 스냅샷과 동전모으기를 분리했습니다. 동전모으기는 페이지 조회 크기 1,000, 청크 크기 1이며 변경 시점에 잠금과 재검증을 수행합니다.
5. **추적과 검증**: 금융거래와 계좌별 원장, 배치 실행 이력을 구분합니다. 정상 경로뿐 아니라 중복 실행과 저장 실패 시 롤백을 테스트했습니다.
6. **한계**: 운영 인증, 온라인 요청 결과 재생, 자동 재시도, 정식 마감과 다중 인스턴스 조정은 추가로 필요합니다.

## 1.4 업무와 데이터의 연결

| 업무 | 입력·기준 | 주요 결과 |
|---|---|---|
| 가입 가능 계좌 조회 | 고객 ID | 이용 중인 저금통이 없고 적합한 일반 입출금계좌가 있으면 목록을 반환합니다. |
| 저금통 개설 | 고객 ID, 선택 계좌 ID | ACCOUNT·ACCOUNT_CONTRACT·COINBOX를 생성합니다. |
| 비우기 | 고객 ID, 저금통 계좌번호 | 저금통의 전액을 근거계좌로 이전하고 거래·원장을 생성합니다. 계좌는 유지합니다. |
| 일별 잔액 저장 | 실행일의 전날이라는 기준일 | ACCOUNT_DAILY_BALANCE를 생성합니다. 실제 값은 조회 시점 잔액입니다. |
| 동전모으기 | 전일 잔액, 현재 잔액·설정·계약·정책 | 저축 또는 업무상 건너뜀을 결정하고 일별 실행 이력을 남깁니다. |
| 해지 | 고객 ID, 저금통 계좌번호 | 남은 잔액을 이전하고 계좌·계약·설정을 종료합니다. |
| ACTIVE 계좌 조회 | 고객 ID | 현재 계좌를 근거계좌와 한 단계 자식 계좌 구조로 반환합니다. |

## 1.5 테이블의 책임

| 테이블 | 답할 수 있는 질문 |
|---|---|
| CUSTOMER | 누구의 계좌이며 고객 상태는 무엇입니까? |
| ACCOUNT | 어떤 계좌이고 현재 잔액·거래 가능 상태·연결 계좌는 무엇입니까? |
| PRODUCT | 어떤 상품군이며 표시할 상품명은 무엇입니까? |
| PRODUCT_VERSION | 어느 적용 기간과 버전의 상품입니까? |
| ACCOUNT_CONTRACT | 이 계좌는 어느 상품 버전에 가입했고 계약 상태는 무엇입니까? |
| COINBOX | 이 저금통은 동전모으기를 사용하는지, 언제 시작했는지 관리합니다. |
| COINBOX_POLICY | 특정 상품 버전의 저금통 한도는 얼마입니까? |
| FINANCIAL_TRANSACTION | 어떤 자금 이동이 언제 얼마만큼 발생했습니까? |
| ACCOUNT_ENTRY | 그 거래가 각 계좌에 어떤 방향·금액·잔액·적요로 반영됐습니까? |
| ACCOUNT_DAILY_BALANCE | 해당 계좌·기준일에 저장한 잔액은 얼마입니까? |
| COIN_SAVING_EXECUTION | 특정 저금통을 특정 날짜에 처리했는지, 결과와 사유는 무엇입니까? |

전체 컬럼과 Enum은 [ERD](../01_ERD.md)를 기준으로 확인합니다. 면접에서는 컬럼을 나열하기보다 각 테이블이 담당하는 업무 책임의 차이를 설명합니다.

## 1.6 클래스의 책임

| 역할 | 주요 클래스 | 설명 |
|---|---|---|
| HTTP 계약 | CoinBoxController, AccountController | 입력을 검증하고 서비스 호출 결과를 응답 DTO로 변환합니다. |
| 온라인 업무 조정 | CoinBoxService | 가입·비우기·해지의 순서와 업무 검증을 담당합니다. |
| 공통 금융 처리 | InternalTransferService | 계좌 검증·잔액 변경·거래·양방향 원장 생성을 모읍니다. |
| 동전모으기 조정 | CoinSavingService | 한 후보의 잠금·최종 검증·이체·실행 이력을 처리합니다. |
| 순수 계산 | CoinSavingAmountCalculator | DB 없이 저축 가능 금액 또는 건너뜀 사유를 계산합니다. |
| 정책 재사용 | CoinSavingPolicyResolver | 한 Step에서 상품 버전별 정책을 최초 조회 후 재사용합니다. |
| 배치 구성 | CoinSavingJobConfig, DailyBalanceJobConfig | 처리 단위와 Reader·Writer·Tasklet을 구성합니다. |
| 조회 결과 조립 | AccountQueryService | 평면 계좌 목록을 부모·자식 응답으로 조립합니다. |
| 인프라 공통 | Snowflake, GlobalExceptionHandler | 식별자 생성과 예외 응답을 담당합니다. |

계층은 Controller → Service → Repository를 기본으로 하며, 관련 코드는 도메인별 패키지로 묶었습니다.

## 1.7 우선 설명할 정합성 규칙

1. 이용 중인 저금통은 고객당 하나라는 규칙을 고객 행 잠금에 참여하는 업무 경로에서 지킵니다. 고객당 한 개를 직접 강제하는 DB UK는 없습니다.
2. 일반 금융 이체는 두 계좌 잔액, 거래 한 건, 원장 두 건을 함께 커밋합니다.
3. 일반 금융 이체에서 출금 계좌의 음수 잔액을 허용하지 않습니다.
4. 같은 저금통·실행일의 동전모으기 결과는 한 행만 저장합니다.
5. 해지는 잔액 정리와 계좌·계약·설정 종료를 같은 트랜잭션으로 처리합니다.
6. 정책은 계약이 참조하는 상품 버전으로 결정합니다. 기존 계약이 무조건 최신 정책을 따라가는 구조가 아닙니다.

테스트용 잔고 증감 API는 거래·원장을 만들지 않으므로 2번 규칙의 적용 대상이 아닙니다.

## 1.8 기술 선택과 근거

| 기술 | 사용한 이유·역할 |
|---|---|
| Java 21 | 빌드 toolchain으로 Java 빌드 기준을 맞춥니다. |
| Spring Boot 4.0.8 | 웹·검증·JPA·배치 등 실행 구성을 통합합니다. |
| JPA + Native Query | 엔티티 변경 감지와 명시적인 조회·잠금 SQL을 조합합니다. |
| JDBC batchUpdate | 일별 잔액 행을 묶어 저장합니다. |
| Spring Batch | Job·Step·청크·실행 메타데이터를 관리합니다. |
| MySQL Testcontainers | MySQL SQL·잠금·제약을 격리된 테스트 DB에서 검증합니다. |
| JaCoCo | 코드 줄·분기의 실행 범위를 확인합니다. |

## 1.9 금융 용어를 과제에 연결하기

- **근거계좌**: 저금통의 자금 유입·회수 대상인 연결 입출금계좌입니다.
- **계좌 상태**: 현재 거래 허용 여부를 나타냅니다. ACTIVE·RESTRICTED·CLOSED입니다.
- **계약 상태**: 상품 가입 관계의 상태입니다. ACTIVE·TERMINATED입니다.
- **원장**: 여기서는 고객 계좌별 입출금 기록을 뜻합니다. 은행 총계정원장·완전한 복식부기 체계를 구현한 것은 아닙니다.
- **업무일과 실행 시각**: 배치 파라미터의 날짜와 실제 DB를 조회한 시각은 구분해야 합니다.
- **멱등성**: 같은 업무를 반복해도 중복 효과를 만들지 않는 성질입니다. 같은 HTTP 응답까지 재생하는 것과는 구분합니다.
- **마감**: 특정 기준 시점의 거래를 확정하는 운영 절차까지 포함할 수 있습니다. 현재 잔액 복사는 정식 마감 시스템이 아닙니다.
