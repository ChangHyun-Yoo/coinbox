# 8. 면접 직전 요약

[전체 목차](README.md)

## 8.1 시작 문장

> 저금통의 네 업무를 별도 계좌 모델로 구현하고, 공통 이체의 원자성·거래 추적·동시성 제어·일별 중복 저축 방지를 중심으로 설계했습니다.

## 8.2 전체 흐름

- 가입: 고객·근거계좌 잠금 → 가입 조건 확인 → 계좌·계약·설정 생성입니다.
- 비우기: 본인 저금통 확인 → 두 계좌 잠금 → 전액 이체·거래·원장 생성입니다. 계좌와 설정은 유지합니다.
- 잔액 배치: ACTIVE·RESTRICTED 현재 잔액 조회 → 전일이라는 기준일로 중복 없이 저장합니다.
- 동전모으기: 후보 페이징 → 한 건 잠금·재검증 → 정책 조회·캐시 → 금액 계산 → 이체 또는 SKIPPED입니다.
- 해지: 고객·두 계좌·설정·계약 잠금 → 잔액 이전 → 계좌·계약·설정 종료입니다.

## 8.4 핵심 질문 12개에 한 줄로 답하기

1. **왜 고객 잠금입니까?** 서로 다른 근거계좌를 통한 동일 고객의 동시 가입도 직렬화하려는 목적입니다.
2. **왜 계좌 ID 순서입니까?** 반대 방향 이체가 잠금 순서를 뒤집어 교착하는 가능성을 줄입니다.
3. **왜 공통 이체입니까?** 잔액·거래·원장 반영과 검증 규칙의 중복을 줄입니다.
4. **MANDATORY의 역할은 무엇입니까?** 기존 트랜잭션 참여를 강제하며 실제 잠금 보장은 호출자의 책임입니다.
5. **왜 계좌와 계약을 분리합니까?** 현재 운영 상태와 상품 가입 관계의 책임이 다르기 때문입니다.
6. **왜 product_type을 중복 저장합니까?** 현재 계좌 유형 판단을 단순화하는 대신 값 일치 책임을 감수했습니다.
7. **왜 거래와 원장을 분리합니까?** 금융 사건 한 건과 계좌별 반영 결과를 각각 추적하기 위해서입니다.
8. **왜 후보를 다시 검증합니까?** 조회는 대상 축소, 잠금 후 검증은 실행 시점 정확성을 담당하기 때문입니다.
9. **왜 실행 이력 UK입니까?** 새 배치 실행에서도 저금통·일자 업무 중복을 최종 방어하기 위해서입니다.
10. **왜 Step 캐시입니까?** 매 실행은 새로 읽되 동일 버전 정책의 실행 내부 반복 조회만 줄이기 위해서입니다.
11. **왜 Testcontainers입니까?** MySQL SQL·잠금·제약을 로컬 개인 DB와 분리해 검증하기 위해서입니다.
12. **가장 중요한 한계는 무엇입니까?** 교차 업무 경쟁 검증, 온라인 요청 멱등성, 정식 마감·실패 복구와 운영 보안이 추가로 필요합니다.

## 8.5 정확하게 구분할 표현

| 피할 표현 | 정확한 표현 |
|---|---|
| '트랜잭션이면 동시성은 해결됩니다.' | 원자성과 경쟁 제어를 구분하고 필요한 잠금을 적용했습니다. |
| '오름차순이면 데드락은 없습니다.' | 일관된 순서로 교착 가능성을 낮췄습니다. |
| 'MANDATORY가 잠금을 확인합니다.' | 기존 트랜잭션만 강제하며 잠금은 호출 규약입니다. |
| 'FOR UPDATE 재조회면 객체도 무조건 최신입니다.' | DB 잠금과 영속성 컨텍스트 객체 최신성을 구분해 검증해야 합니다. |
| '이체 때 두 계약을 모두 검사합니다.' | 공통 이체는 계좌 상태를, 일부 상위 업무는 저금통 계약을 확인합니다. |
| '배치는 실패해도 다음 건을 처리합니다.' | 현재는 실패 청크 롤백 후 Step이 중단됩니다. |
| 'Spring Batch가 자동 재시도합니다.' | 현재 Retry·Skip 설정과 실패 Job Restart API는 없습니다. |
| 'FAILED는 DB에 항상 남습니다.' | Enum은 있지만 시스템 실패 이력의 독립 저장은 구현하지 않았습니다. |
| '정책은 하루 동안 캐시합니다.' | 같은 날이어도 새 Step 실행이면 다시 조회합니다. |
| '계약은 항상 최신 정책을 사용합니다.' | 계약이 참조하는 상품 버전의 정책을 사용합니다. |
| '자정 배치로 정확한 전일 마감을 보장합니다.' | 현재는 조회 시점 잔액을 기준일에 저장하는 단순 스냅샷입니다. |
| 'FK는 모두 DB가 보장합니다.' | 현재 ERD FK는 논리 참조이며 물리 FK는 생성하지 않습니다. |
| '고객당 하나를 UK로 보장합니다.' | 해당 UK 없이 고객 행 잠금 규약으로 관리합니다. |
| 'UK가 있으니 비우기 재요청도 안전합니다.' | 배치 업무 UK와 온라인 요청 멱등성은 별개입니다. |
| '모든 잔액 변경은 원장을 남깁니다.' | 초기 데이터와 테스트용 직접 잔고 조정은 예외입니다. |
| '모든 조회가 JPA입니다.' | 업무 조회에 Native JPA를 사용하지만 Batch Reader는 JDBC입니다. |
| '/internal은 외부에서 호출할 수 없습니다.' | 현재 경로 구분일 뿐 인증·인가가 구현되어 있지 않습니다. |
| '커버리지가 높아 금융 안정성이 증명됐습니다.' | 실행 범위 지표이며 검증 시나리오·assertion과 함께 평가해야 합니다. |

## 8.7 답변을 마무리하는 방식

모르는 질문에는 추측을 확정 사실처럼 말하지 않습니다.

> 그 부분은 현재 구현에서 검증하지 않았습니다. 다만 이 경로의 트랜잭션과 조회 방식 때문에 이런 위험을 먼저 확인하겠습니다. 경쟁 시점을 통제한 테스트와 실제 SQL을 확인한 뒤 판단하겠습니다.

선택한 설계가 비판받으면 대안을 인정하고 현재 요구·비용·검증 범위를 설명합니다. 이 과제에서 직접 운영한 적 없는 대규모 장애 경험이나 검증하지 않은 처리량을 만들어 말하지 않습니다.
