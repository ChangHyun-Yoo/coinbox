# 7. 설계 검토와 모의면접

[목차](README.md) · [직전 복습](08_QUICK_REVIEW.md)

## 7.1 이 문서의 목적

선택한 설계의 장점을 설명하되 한계나 미검증 영역을 숨기지 않는 답변을 준비합니다. '개선 가능성이 있다'와 '실제 오류를 재현했다'는 다른 주장입니다. 아래 추가 검증 사항은 이번 문서 작성 중 정적 코드 확인으로 도출했으며 코드를 수정하거나 장애를 재현한 결과가 아닙니다.

## 7.2 강점으로 설명할 부분

| 강점 | 구체적인 근거 |
|---|---|
| 업무와 데이터가 연결됩니다. | 네 업무의 시퀀스·ERD·예시 데이터·클래스 문서를 제공합니다. |
| 금융 변경을 공통화했습니다. | InternalTransferService에 잔액·거래·원장 처리를 모았습니다. |
| 경쟁과 실패를 고려했습니다. | 고객 잠금, 계좌 잠금, UK, 실제 DB 롤백 테스트가 있습니다. |
| 반복 조회를 구분했습니다. | 정책은 Step 캐시, 잠긴 계좌는 재사용, 현재 상태는 재검증합니다. |
| 재현 가능한 평가 환경을 제공합니다. | 초기 데이터, Swagger, Gradle, MySQL Testcontainers를 사용합니다. |

## 7.3 추가 검증 항목

### 7.3.1 잠금 전 조회한 Account의 최신성

- **코드에서 확인한 사실:** 비우기·해지는 먼저 Account를 일반 조회하고 이후 Native FOR UPDATE로 동일 엔티티를 조회합니다.
- **검증이 필요한 추론:** 영속성 컨텍스트가 기존 관리 객체를 재사용하면 잠금 대기 중 커밋된 잔액·상태가 Java 객체에 기대대로 반영되지 않을 수 있습니다.
- **검증 방법:** T1이 비우기의 사전 조회 직후 대기하도록 하고 T2가 같은 저금통의 잔액을 변경·커밋한 뒤 T1을 진행시킵니다. 최종 두 잔액, 거래 금액, 원장 before/after를 함께 확인합니다.
- **통과 기준:** 잠금으로 확정한 최신 잔액을 사용하고 돈의 유실·과다 이전이 없어야 합니다.
- **실패 시 검토:** 사전 조회는 식별자 projection으로 제한하고 잠금 조회에서 처음 엔티티를 관리하거나, 적절한 refresh와 조회 순서를 검토합니다. 아직 적용한 수정은 아닙니다.

[관련 서비스](../../src/main/java/com/kakaobank/coinbox/coinbox/service/CoinBoxService.java) · [영속성 컨텍스트와 refresh](https://jakarta.ee/specifications/persistence/3.2/apidocs/jakarta.persistence/jakarta/persistence/entitymanager)

### 7.3.2 지정 기준일과 실제 잔액 조회 시각

- **확인한 사실:** 잔액 Tasklet은 현재 계좌 잔액을 조회하고 파라미터의 balanceDate를 저장합니다.
- **한계:** 자정 스케줄 지연·과거 날짜 수동 실행에서 정확한 과거 마감 잔액을 복원하지 않습니다.
- **검증 방법:** 자정 이후 거래가 반영된 상태에서 전일 기준 배치를 실행해 어떤 값이 저장되는지 확인합니다.
- **설계 선택:** 정확한 마감이 필요하면 기준 시각·회계일·지연 거래·원장 집계·마감 완료 상태부터 정의합니다.

### 7.3.3 온라인 비우기 요청의 재전송

- **확인한 사실:** 요청 단위 Idempotency-Key나 응답 저장 테이블이 없습니다.
- **한계:** 첫 비우기 성공 후 새 자금이 들어오고 이전 요청이 재전송되면 새 잔액을 비울 수 있습니다.
- **검증 방법:** 첫 응답을 받지 못한 상황을 모사하고 중간 입금 후 같은 요청을 다시 호출합니다.
- **개선안:** 인증 주체·업무 요청 키·요청 해시·상태·결과를 원자적으로 관리합니다.

### 7.3.4 Snowflake 선할당 ID와 save의 SQL 수

- **확인한 사실:** ID는 애플리케이션에서 생성하며 엔티티에 별도 @Version·Persistable 신규 판단 구현은 없습니다.
- **검증 대상:** 신규 save의 merge 경로에서 추가 조회가 발생하는지 SQL 수를 측정합니다.
- **개선안:** 실제 필요가 확인되면 신규 상태 판별이나 명시적인 persist 경로를 검토합니다.

### 7.3.5 실행 경계와 시각의 일관성

- **확인한 사실:** 날짜 계산과 일부 감사 시각에는 주입한 Clock을 사용하지만 공통 이체 시각과 오류 응답 등에는 LocalDateTime.now()를 사용합니다.
- **검증 대상:** JVM 기본 시간대가 서울이 아닐 때 업무일·거래 시각의 일관성과 테스트의 재현성을 확인합니다.
- **개선안:** 업무 날짜와 저장 타임스탬프의 시간대 규약을 정하고 Clock 사용을 통일합니다.

## 7.4 운영 전 우선순위

아래는 개인 면접 준비용 개선 순서 제안입니다. 새 기능 구현을 완료했다는 뜻은 아닙니다.

| 우선순위 | 항목 | 이유 |
|---|---|---|
| P0 | 교차 업무 경쟁과 JPA 객체 최신성 검증 | 자금 정합성에 직접 영향을 줄 수 있는 가정을 먼저 검증합니다. |
| P0 | 인증·인가와 테스트 API 격리 | 헤더 위조와 임의 잔액 변경을 막아야 합니다. |
| P0 | ddl-auto=create 제거, 마이그레이션·데이터 보존 | 재시작 데이터 손실을 방지합니다. |
| P1 | 온라인 요청 멱등성과 결과 확인 | 응답 유실 후 안전한 재요청이 필요합니다. |
| P1 | 마감 기준과 배치 실패 복구 | 일별 결과의 정확성과 재처리 절차를 확보합니다. |
| P1 | 물리 FK·필요 제약·정합성 대사 | 우회 쓰기와 장기 데이터 오류를 방어합니다. |
| P2 | 분산 스케줄·Snowflake 노드 관리 | 다중 인스턴스에서 중복 실행과 키 충돌을 방지합니다. |
| P2 | 성능 측정·분할 처리·관측성 | 부하가 커질 때 처리량과 장애 진단을 개선합니다. |

## 7.5 상황형 질문과 답변

### R01. '고객당 하나라면서 DB 제약이 없는데 안전하다고 할 수 있습니까?'

> 모든 쓰기 경로까지 보장하는 것은 아닙니다. 현재 개설·해지는 같은 고객 행을 잠그고 이용 중인 저금통 여부를 확인하므로 해당 경로의 동시 가입을 제어합니다. 직접 SQL 등 잠금 규약을 지키지 않는 경로까지 막으려면 추가 DB 제약이 필요합니다.

### R02. '원장 두 건 중 한 건만 저장되면 어떻게 합니까?'

> 같은 트랜잭션의 잔액·거래·원장 변경을 모두 롤백합니다. 원장 한 건만 반영된 상태로 커밋하지 않도록 구성했고, 실제 DB 저장 실패를 유도한 롤백 테스트를 작성했습니다.

### R03. 'DB 커밋은 됐는데 고객이 타임아웃을 받았다면요?'

> 재이체하지 않고 먼저 기존 처리 결과를 확인해야 합니다. DB에는 이미 커밋됐을 수 있기 때문입니다. 현재는 요청 키 기반 결과 조회·재사용 기능이 없으므로, 이를 추가해 같은 요청에는 기존 결과를 반환하도록 보완하겠습니다.

### R04. '동전모으기가 한 계좌에서 실패하면 뒤 계좌는 어떻게 됩니까?'

> 해당 청크는 롤백되고 Step이 중단돼 뒤의 후보는 처리되지 않습니다. 앞서 커밋한 결과는 유지됩니다. 오류 원인을 해결하고 같은 날짜로 재실행하면 이미 결과가 있는 대상을 제외하고 남은 후보를 처리합니다.

### R05. '전일 잔액 누락으로 SKIPPED였는데 잔액 자료를 복구했다면요?'

> 자료를 복구해도 현재 구조에서는 자동 재처리되지 않습니다. SKIPPED 이력도 해당 날짜의 처리 결과로 보아 Reader에서 제외하기 때문입니다. 재처리하려면 보정 대상과 기존 결과의 처리 방식, 중복 방지 규칙을 별도로 정해야 합니다.

### R06. '동일 날짜 배치를 두 서버가 동시에 실행하면요?'

> 두 서버에서 각각 배치가 시작될 수 있습니다. 같은 저금통의 처리는 DB 잠금과 실행 이력 UK로 중복 반영을 방어하지만, 중복 조회와 잠금 대기는 발생합니다. 또한 현재 Snowflake 노드 ID가 0으로 고정돼 있으므로 다중 서버 실행 전 노드 ID를 분리해야 합니다.

### R07. '저금통이 1,000만 개가 되면 지금 구조가 충분합니까?'

> 충분하다고 판단할 근거가 없습니다. 현재 처리량을 그 규모에서 검증하지 않았고, 잔액 Tasklet도 전체 대상을 메모리에 적재합니다. 먼저 목표 완료 시간과 온라인 응답 기준을 정해 SQL·커밋·잠금 대기를 측정하고, 잔액 분할 처리와 동전모으기 파티셔닝을 검토하겠습니다.

### R08. '과제치고 상품 버전 구조가 과하지 않습니까?'

> 정책이 하나로 고정된다면 더 단순한 구조도 가능합니다. 현재는 가입 당시 정책을 버전으로 식별할 수 있도록 구성했고, 그 대신 테이블과 조인이 늘어나는 비용을 선택했습니다.

### R09. '실제 저금통 약관을 모두 만족합니까?'

> 전체 충족을 주장할 수는 없습니다. 이 과제는 가입·비우기·동전모으기·해지를 중심으로 구현했고 이자·수수료·정식 마감은 제외했습니다. 구현한 가입 조건·한도·자동저축 기준·해지 조건은 제출 당시 참조한 약관과 상품설명서에 대조해 설명해야 합니다.

### R10. 'AI를 사용했다면 본인이 이해하고 구현한 부분은 무엇입니까?'

본인의 실제 기여를 넣어 완성하는 답변입니다.

> AI는 [도움을 받은 작업]에 활용했고, 저는 [직접 판단한 설계]를 결정하고 [직접 실행한 테스트와 확인한 결과]를 검증했습니다. 그중 [구체적인 기능 하나]는 데이터 흐름과 잠금·트랜잭션 경계까지 설명할 수 있습니다.

## 7.6 운영 확장 방향 답변

> 기능을 늘리기 전에 금융 정합성 가정의 교차 업무 테스트와 데이터 보존·인증을 먼저 보강하겠습니다. 이후 온라인 요청 멱등성, 정확한 일별 기준 잔액과 배치 복구를 설계하겠습니다. 정상 흐름보다 실패 이후 어떤 결과가 남는지 설명할 수 있는 구조를 우선하겠습니다.

## 7.7 45분 모의면접 진행안

| 시간 | 질문 범위 | 확인할 내용 |
|---|---|---|
| 0~5분 | 1분 소개, 전체 구조 | 기능 나열을 넘어 데이터 흐름을 설명하는지 확인합니다. |
| 5~15분 | 가입·비우기·동전모으기·해지 | 검증·잠금·변경·실패 결과를 연결하는지 확인합니다. |
| 15~25분 | 고객 잠금·공통 이체·MANDATORY·UK | 보장 범위와 반례를 설명하는지 확인합니다. |
| 25~33분 | 페이지/청크·캐시·실패 재실행 | 프레임워크 기능과 구현 옵션을 구분하는지 확인합니다. |
| 33~40분 | 테스트·SQL·운영 한계 | 근거 있는 검증과 우선순위를 설명하는지 확인합니다. |
| 40~45분 | AI 사용·설계 이해·질문 | 본인 기여와 현재 설계의 근거를 구체적으로 설명하는지 확인합니다. |

기본 질문에는 해당 내용만 답합니다. 이후 대안·실패·동시성·검증에 관한 꼬리질문을 따로 추가해 연습합니다.

## 7.8 자기 점검 기준

각 항목을 0~2점으로 점검합니다.

1. 첫 문장에서 질문에 대한 결론을 답했습니까?
2. 질문이 묻는 모든 항목을 빠짐없이 설명했습니까?
3. 이유와 구현 근거가 질문에 직접 연결됩니까?
4. 질문과 무관한 기능·주의사항·개선안을 덧붙이지 않았습니까?
5. 실제 구현과 설명이 일치합니까?

점수는 답변 연습의 보완점을 찾기 위한 기준입니다.
