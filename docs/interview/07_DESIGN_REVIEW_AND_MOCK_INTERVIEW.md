# 7. 설계 검토와 모의면접

[목차](README.md) · [직전 복습](08_QUICK_REVIEW.md)

## 7.1 이 문서의 목적

선택한 설계의 장점을 설명하되 한계나 미검증 영역을 숨기지 않는 답변을 준비합니다. '개선 가능성이 있다'와 '실제 오류를 재현했다'는 다른 주장입니다. 아래 추가 검증 사항은 이번 문서 작성 중 정적 코드 확인으로 도출했으며 코드를 수정하거나 장애를 재현한 결과가 아닙니다.

## 7.2 강점으로 설명할 부분

| 강점 | 구체적인 근거 | 함께 인정할 한계 |
|---|---|---|
| 업무와 데이터가 연결됩니다. | 네 업무의 시퀀스·ERD·예시 데이터·클래스 문서를 제공합니다. | 문서가 있다고 모든 규칙 준수가 자동 증명되지는 않습니다. |
| 금융 변경을 공통화했습니다. | InternalTransferService에 잔액·거래·원장 처리를 모았습니다. | 상품 검증은 상위 서비스와의 책임 경계를 지켜야 합니다. |
| 경쟁과 실패를 고려했습니다. | 고객 잠금, 계좌 잠금, UK, 실제 DB 롤백 테스트가 있습니다. | 모든 경쟁 조합·응답 유실·운영 장애는 검증하지 않았습니다. |
| 반복 조회를 구분했습니다. | 정책은 Step 캐시, 잠긴 계좌는 재사용, 현재 상태는 재검증합니다. | 전역 최신성이나 대규모 성능 수치는 보장하지 않습니다. |
| 재현 가능한 평가 환경을 제공합니다. | 초기 데이터, Swagger, Gradle, MySQL Testcontainers를 사용합니다. | 운영용 인증·배포·데이터 보존 설정과는 다릅니다. |

## 7.3 추가 검증 항목

### 7.3.1 잠금 전 조회한 Account의 최신성

- **코드에서 확인한 사실:** 비우기·해지는 먼저 Account를 일반 조회하고 이후 Native FOR UPDATE로 동일 엔티티를 조회합니다.
- **검증이 필요한 추론:** 영속성 컨텍스트가 기존 관리 객체를 재사용하면 잠금 대기 중 커밋된 잔액·상태가 Java 객체에 기대대로 반영되지 않을 수 있습니다.
- **검증 방법:** T1이 비우기의 사전 조회 직후 대기하도록 하고 T2가 같은 저금통의 잔액을 변경·커밋한 뒤 T1을 진행시킵니다. 최종 두 잔액, 거래 금액, 원장 before/after를 함께 확인합니다.
- **통과 기준:** 잠금으로 확정한 최신 잔액을 사용하고 돈의 유실·과다 이전이 없어야 합니다.
- **실패 시 검토:** 사전 조회는 식별자 projection으로 제한하고 잠금 조회에서 처음 엔티티를 관리하거나, 적절한 refresh와 조회 순서를 검토합니다. 아직 적용한 수정은 아닙니다.

[관련 서비스](../../src/main/java/com/kakaobank/coinbox/coinbox/service/CoinBoxService.java) · [영속성 컨텍스트와 refresh](https://jakarta.ee/specifications/persistence/3.2/apidocs/jakarta.persistence/jakarta/persistence/entitymanager)

### 7.3.2 지정 기준일과 실제 잔액 조회 시각

- **확인한 사실:** 잔액 Tasklet은 현재 계좌 잔액을 조회하고 파라미터의 balanceDate를 저장합니다.
- **한계:** 자정 스케줄 지연·과거 날짜 수동 실행에서 정확한 과거 마감 잔액을 복원하지 않습니다.
- **검증 방법:** 자정 이후 거래가 반영된 상태에서 전일 기준 배치를 실행해 어떤 값이 저장되는지 확인합니다.
- **설계 선택:** 정확한 마감이 필요하면 기준 시각·회계일·지연 거래·원장 집계·마감 완료 상태부터 정의합니다.

### 7.3.3 온라인 비우기 요청의 재전송

- **확인한 사실:** 요청 단위 Idempotency-Key나 응답 저장 테이블이 없습니다.
- **한계:** 첫 비우기 성공 후 새 자금이 들어오고 이전 요청이 재전송되면 새 잔액을 비울 수 있습니다.
- **검증 방법:** 첫 응답을 받지 못한 상황을 모사하고 중간 입금 후 같은 요청을 다시 호출합니다.
- **개선안:** 인증 주체·업무 요청 키·요청 해시·상태·결과를 원자적으로 관리합니다.

### 7.3.4 Snowflake 선할당 ID와 save의 SQL 수

- **확인한 사실:** ID는 애플리케이션에서 생성하며 엔티티에 별도 @Version·Persistable 신규 판단 구현은 없습니다.
- **검증 대상:** 신규 save의 merge 경로에서 추가 조회가 발생하는지 SQL 수를 측정합니다.
- **개선안:** 실제 필요가 확인되면 신규 상태 판별이나 명시적인 persist 경로를 검토합니다.

### 7.3.5 실행 경계와 시각의 일관성

- **확인한 사실:** 날짜 계산과 일부 감사 시각에는 주입한 Clock을 사용하지만 공통 이체 시각과 오류 응답 등에는 LocalDateTime.now()를 사용합니다.
- **검증 대상:** JVM 기본 시간대가 서울이 아닐 때 업무일·거래 시각의 일관성과 테스트의 재현성을 확인합니다.
- **개선안:** 업무 날짜와 저장 타임스탬프의 시간대 규약을 정하고 Clock 사용을 통일합니다.

## 7.4 운영 전 우선순위

아래는 개인 면접 준비용 개선 순서 제안입니다. 새 기능 구현을 완료했다는 뜻은 아닙니다.

| 우선순위 | 항목 | 이유 |
|---|---|---|
| P0 | 교차 업무 경쟁과 JPA 객체 최신성 검증 | 자금 정합성에 직접 영향을 줄 수 있는 가정을 먼저 검증합니다. |
| P0 | 인증·인가와 테스트 API 격리 | 헤더 위조와 임의 잔액 변경을 막아야 합니다. |
| P0 | ddl-auto=create 제거, 마이그레이션·데이터 보존 | 재시작 데이터 손실을 방지합니다. |
| P1 | 온라인 요청 멱등성과 결과 확인 | 응답 유실 후 안전한 재요청이 필요합니다. |
| P1 | 마감 기준과 배치 실패 복구 | 일별 결과의 정확성과 재처리 절차를 확보합니다. |
| P1 | 물리 FK·필요 제약·정합성 대사 | 우회 쓰기와 장기 데이터 오류를 방어합니다. |
| P2 | 분산 스케줄·Snowflake 노드 관리 | 다중 인스턴스에서 중복 실행과 키 충돌을 방지합니다. |
| P2 | 성능 측정·분할 처리·관측성 | 부하가 커질 때 처리량과 장애 진단을 개선합니다. |

실제 운영에서는 보안·데이터 보존·금융 정확성을 배포 전 조건으로 함께 다뤄야 합니다. 학습용 P0/P1 분류가 운영 위험을 방치하라는 뜻은 아닙니다.

## 7.5 상황형 질문과 답변

### R01. '고객당 하나라면서 DB 제약이 없는데 안전하다고 할 수 있습니까?'

> 현재는 고객 행을 공통 잠금 대상으로 삼고 개설과 해지가 그 규약을 따르는 애플리케이션 경로에서 직렬화합니다. 다른 쓰기 경로까지 DB가 직접 강제하는 구조는 아니라는 한계가 있습니다. 해당 제약을 추가하지 않은 선택과 보장 범위를 구분해서 설명하겠습니다.

DB 대안으로는 고객별 현재 저금통 연결 테이블의 customer_id 유일 키나 조건부 유일성을 표현하는 모델을 검토할 수 있습니다. 현재 적용한 것은 아니며, 해지·재가입과 이력 보존 규칙까지 함께 설계해야 합니다.

### R02. '원장 두 건 중 한 건만 저장되면 어떻게 합니까?'

> 일반 이체에서는 두 계좌 잔액과 거래·원장을 같은 트랜잭션에 넣었습니다. 원장 저장에 실패하면 전체를 롤백하도록 하고, 실제 DB 제약 실패를 유도한 테스트로 확인했습니다. 반대로 운영자가 직접 DB를 변경한 경우까지 같은 보장이 적용되지는 않아 권한 통제와 대사가 필요합니다.

### R03. 'DB 커밋은 됐는데 고객이 타임아웃을 받았다면요?'

> 고객 입장에서 실패처럼 보여도 DB에는 성공했을 수 있으므로 무조건 같은 변경을 다시 실행하지 않겠습니다. 현재 프로젝트는 온라인 요청 결과 재생이 없다는 한계가 있습니다. 운영에서는 요청 키로 기존 처리 상태를 조회하고 확정된 응답을 반환하는 방식이 필요합니다.

### R04. '동전모으기가 한 계좌에서 실패하면 뒤 계좌는 어떻게 됩니까?'

> 현재는 해당 청크가 롤백되고 Step이 실패해 뒤의 후보는 처리되지 않습니다. 앞서 커밋한 계좌는 유지됩니다. 실패 원인을 해결하고 같은 업무 날짜로 새 실행을 시작하면 이미 결과가 있는 대상은 제외합니다. 자동 Retry·Skip이 구현됐다고 설명하지 않겠습니다.

### R05. '전일 잔액 누락으로 SKIPPED였는데 잔액 자료를 복구했다면요?'

> 현재 같은 저금통·실행일 이력이 이미 있으면 Reader에서 제외하므로 자동으로 재처리하지 않습니다. 보정 대상 선정과 승인, 기존 결과의 취급, 추가 처리 이력과 중복 방지 규칙을 별도로 정해야 합니다. 운영에서 기존 이력을 무작정 삭제하고 다시 돌리는 방식은 피하겠습니다.

### R06. '동일 날짜 배치를 두 서버가 동시에 실행하면요?'

> 현재 스케줄러는 서버별로 동작하므로 두 실행이 시작될 수 있습니다. 업무 잠금과 UK가 중복 금융 반영을 방어하도록 구성했지만 불필요한 조회와 잠금·메타데이터 경쟁은 남습니다. 운영에서는 실행 주체를 분리하거나 분산 실행 잠금을 도입하고, Snowflake 노드 ID도 별도로 할당해야 합니다.

### R07. '저금통이 1,000만 개가 되면 지금 구조가 충분합니까?'

> 현재 규모에서 그 처리량을 검증하지 않았으므로 충분하다고 말할 수 없습니다. 실행 제한 시간과 온라인 SLA부터 정한 뒤 후보 SQL·인덱스·건당 쿼리·커밋 비용·잠금 대기를 측정하겠습니다. 잔액 Tasklet의 전체 메모리 적재를 분할하고, 동전모으기는 독립 범위를 기준으로 파티셔닝을 검토하겠습니다.

### R08. '과제치고 상품 버전 구조가 과하지 않습니까?'

> 단일 고정 정책만 요구된다면 더 단순한 구조도 가능합니다. 저는 가입 당시 정책의 식별과 현재 계좌 운영 정보를 분리하는 방향으로 구성했고, 테이블과 조인이 늘어나는 비용을 감수했습니다. 운영자용 버전 관리와 계약 전환 기능까지 구현한 것은 아니며 요구 범위에 따라 축소할 수 있습니다.

### R09. '실제 저금통 약관을 모두 만족합니까?'

> 구현한 규칙을 제출 당시 확인한 약관·상품설명서의 조항과 연결해 설명하겠습니다. 이자·수수료·정식 마감 등 제외한 범위도 명시하겠습니다. 현재 시점 상품 규정이나 은행 내부 처리와 완전히 같다고 단정하지 않겠습니다.

준비 시에는 실제로 참조했던 문서의 제목·시행일과 가입 자격, 한도, 자동저축 일시·금액 기준, 해지 조건을 대조합니다. 이 자료에는 제출 당시 약관 원본의 버전 정보가 확정되어 있지 않으므로 임의로 작성하지 않았습니다.

### R10. 'AI를 사용했다면 본인이 이해하고 구현한 부분은 무엇입니까?'

> AI를 사용한 범위와 제가 직접 판단·검토·검증한 범위를 구분해 설명하겠습니다. 설계 초안이나 코드 생성의 도움을 받았더라도 선택한 데이터 모델, 잠금 순서, 트랜잭션 경계와 테스트 결과를 제 말로 설명할 수 있어야 한다고 생각합니다.

실제 사실을 아래 형식으로 개인적으로 채웁니다. 이 자료는 확인되지 않은 독자 구현·운영 경험을 대신 만들어 주지 않습니다.

- AI의 도움을 받은 작업: 실제 사용 범위입니다.
- 본인이 판단한 설계: 구현 근거와 선택 이유입니다.
- 본인이 직접 실행·확인한 검증: 명령·테스트·결과입니다.
- 아직 이해가 부족한 부분: 추가로 확인할 코드와 개념입니다.

## 7.6 운영 확장 방향 답변

> 기능을 늘리기 전에 금융 정합성 가정의 교차 업무 테스트와 데이터 보존·인증을 먼저 보강하겠습니다. 이후 온라인 요청 멱등성, 정확한 일별 기준 잔액과 배치 복구를 설계하겠습니다. 정상 흐름보다 실패 이후 어떤 결과가 남는지 설명할 수 있는 구조를 우선하겠습니다.

## 7.7 45분 모의면접 진행안

| 시간 | 질문 범위 | 확인할 내용 |
|---|---|---|
| 0~5분 | 1분 소개, 전체 구조 | 기능 나열을 넘어 데이터 흐름을 설명하는지 확인합니다. |

| 25~33분 | 페이지/청크·캐시·실패 재실행 | 프레임워크 기능과 구현 옵션을 구분하는지 확인합니다. |
| 33~40분 | 테스트·SQL·운영 한계 | 근거 있는 검증과 우선순위를 설명하는지 확인합니다. |
| 40~45분 | AI 사용·설계 이해·질문 | 본인 기여와 현재 설계의 근거를 구체적으로 설명하는지 확인합니다. |

질문 하나를 답하면 '왜 다른 방법은 안 썼습니까?', '중간에 실패하면요?', '동시에 실행되면요?', '무엇으로 검증했습니까?'를 추가합니다. 실제 채용팀의 평가표가 아니라 개인 연습용 구성입니다.

## 7.8 자기 점검 기준

각 답변을 0~2점으로 점검합니다.

1. 결론을 먼저 말했습니까?
2. 실제 클래스·테이블·쿼리·테스트로 근거를 설명했습니까?
3. 선택 이유와 대안을 함께 말했습니까?
4. 실패·경쟁·재실행 시 결과를 설명했습니까?
5. 미구현·미측정을 솔직하게 구분했습니까?

점수는 합격 예측이 아니라 연습의 빈틈을 찾기 위한 도구입니다. '문제가 없습니다'보다 '이 범위는 이렇게 보장했고 이 지점은 추가 검증이 필요합니다'가 정확한 설명입니다.
